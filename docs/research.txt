Architecting a Git-Versioned SQLite Database: A C-Based Virtual File System Approach
1. Introduction and Architectural Imperative
The convergence of relational database management systems (RDBMS) and distributed version control systems (DVCS) represents a profound paradigm shift in modern data architecture. Historically, databases have been optimized for high-throughput, in-place mutations, operating under the assumption that the present state is the only state of consequence. Conversely, version control systems like Git have been optimized for tracking the historical evolution of file-based assets over time, prioritizing cryptographic certainty and branching capabilities over transactional mutation speed. Bridging these two domains offers the ability to branch, merge, and rollback data states with the same agility utilized in source code management.
Designing a database that achieves both relational query robustness and Git-native versioning introduces immediate architectural friction. While entirely new database engines have been built to solve this problem—such as those utilizing Probabilistic B-Trees (Prolly Trees) to achieve content-addressed structural sharing 1—such systems inevitably diverge from established industry standards. The requirement to maintain the exact query language, schema model, and execution semantics of SQLite while enabling efficient Git-based versioning strictly prohibits a ground-up rewrite of the query execution planner or the adoption of non-standard SQL dialects.
To fulfill these rigorous requirements, a radical architectural inversion is required. Modifying the underlying data structure of SQLite from a standard B-Tree to a Prolly Tree would necessitate a hard fork of the core database engine, destroying upstream compatibility, portability, and reliance on the standard SQLite query planner. Instead, the optimal solution lies in exploiting SQLite's highly decoupled internal architecture. By intercepting the communication between the database engine and the host operating system, it is possible to remap the logical address space of a contiguous database file into a discretized collection of fixed-size binary data pages.3
When these discrete pages are stored in a designated directory hierarchy, Git can track the state of the database precisely at the page level. The primary challenge, therefore, is not whether Git can track binary files—a common misconception—but whether it can store highly mutable, non-plaintext binary pages efficiently without succumbing to catastrophic repository bloat.4 This report exhaustively details the software architecture required to build this system using pure C. It explores the mechanics of the SQLite Virtual File System (VFS), the physics of B-Tree byte shifting relative to Git's delta compression algorithms, the mechanics of out-of-band manual Git snapshotting via the standard command-line interface, and the C-based VFS necessary to achieve high-performance execution.
2. Evaluation of Competing Versioned Database Architectures
Before establishing the technical specifications for a page-segmented SQLite implementation, it is critical to evaluate the existing landscape of versioned databases to understand why a custom Virtual File System (VFS) approach is uniquely mandated by the portability requirements.
2.1 The Prolly Tree Approach
The most prominent data structure utilized in contemporary version-controlled databases (such as Dolt) is the Prolly Tree, short for Probabilistic B-Tree.1 A Prolly Tree is a block-oriented search tree that fuses the ordered access characteristics of a standard B-Tree with the cryptographic verification properties of a Merkle Tree.2
Unlike traditional B-Trees, which utilize fixed-size pages, Prolly Trees rely on content-defined chunking. A rolling hash algorithm traverses the serialized key-value pairs, and whenever the hash output falls below a predefined threshold, a structural block boundary is declared.2 This mechanism ensures that the tree is "history-independent" or "unicit".1 Whether a dataset is inserted sequentially or entirely out of order, the resulting Prolly Tree will possess the exact same structure and the exact same cryptographic root hash.1 This history independence makes determining the delta between two massive datasets a mathematically trivial operation, requiring a simple recursive hash comparison down the tree branches.1
2.2 The Incompatibility of Prolly Trees with SQLite Portability
While Prolly Trees represent an elegant solution for native version-controlled databases, they are fundamentally incompatible with the requirement of strict SQLite portability.

Integrating a Prolly Tree into SQLite would require replacing the entire internal B-Tree module (btree.c), which is intricately coupled with the Virtual Database Engine (VDBE).8 Such a modification would fork the codebase, severing the ability to apply upstream SQLite security patches, optimizations, and new SQL features. To maintain the exact schema model and query language of SQLite in a highly portable manner, the internal B-Tree logic must remain completely untouched. The version control mechanics must be pushed further down the stack to the operating system abstraction layer.
3. Deconstructing the SQLite Storage Pipeline
To design a highly efficient, Git-compatible storage backend, a nuanced understanding of SQLite’s internal execution pipeline is imperative. SQLite is not a monolithic application; it is a stack of distinct, modular components separated by well-defined C-struct interfaces.3
3.1 The Frontend and the Virtual Database Engine (VDBE)
When a SQL query is submitted to SQLite, it passes through the Tokenizer, Parser, and Code Generator. This frontend compilation process translates the plaintext SQL into a sequence of bytecode instructions.7 This bytecode is then handed off to the Virtual Database Engine (VDBE). The VDBE acts as a specialized virtual CPU whose instruction set is tailored exclusively for database operations—scanning tables, comparing keys, managing cursors, and enforcing transactional constraints.8
Crucially, the VDBE does not possess any awareness of how data is physically laid out on disk. It communicates exclusively with the B-Tree module.
3.2 The B-Tree Module
In SQLite, every table and every index is stored in its own separate B-Tree structure. Specifically, SQLite utilizes a B+Tree variant for table storage (where all row payloads reside exclusively in the leaf nodes) and standard B-Trees for index storage (where keys reside in both interior and leaf nodes).7
The B-Tree module handles the logical organization of data, executing search, insertion, and deletion algorithms while maintaining tree balance.8 However, the B-Tree module itself is also completely oblivious to the host file system. It conceptualizes the database as a single, infinitely addressable array of fixed-size blocks known as "pages".7
3.3 The Pager and the Virtual File System (VFS) Abstraction
The responsibility of translating the B-Tree's logical page requests into physical disk operations falls to the Pager module. The Pager manages the in-memory cache of pages, handles the write-ahead log (WAL) or rollback journal, and ensures the ACID (Atomicity, Consistency, Isolation, Durability) properties of transactions.7
Beneath the Pager lies the Virtual File System (VFS). The VFS is the lowest layer in the SQLite architecture and serves as the sole boundary between the database engine and the host operating system.3 Whenever the Pager needs to read a page, write a page, truncate the database, or acquire an exclusive lock, it invokes methods defined in a sqlite3_vfs C-struct.10
By default, SQLite provides VFS implementations for Unix and Windows that map the Pager's requests directly to a single monolithic file on the hard drive.3 However, SQLite exposes a public API, sqlite3_vfs_register(), allowing developers to inject custom VFS implementations at runtime.3 This architectural seam is the key to fulfilling the system requirements. By implementing a custom VFS in C, the monolithic file illusion maintained by the Pager can be shattered, allowing the custom software to redirect read and write operations to thousands of individual, Git-tracked binary page files.



4. Architecting the Page-to-File Storage Paradigm
To optimize the architecture for Git versioning, the custom VFS must cleanly intercept SQLite's contiguous byte addressing and map it into a segmented, distributed file system structure.
4.1 Implementing the sqlite3_io_methods Struct
When SQLite opens a database via the VFS, the custom xOpen method returns a sqlite3_file struct.3 This struct contains a pointer to an sqlite3_io_methods object, which defines the function pointers for all subsequent I/O operations against that specific database.11 To achieve the page-to-file mapping, the C application must implement the following critical methods:

Method Signature
Custom VFS Implementation Logic
xRead(sqlite3_file*, void* buffer, int amount, sqlite3_int64 offset)
The VFS calculates the target page number using offset / page_size. It constructs the corresponding file path (e.g., 000003.bin), reads exactly amount bytes from that specific file into the C memory buffer, and returns SQLITE_OK.11
xWrite(sqlite3_file*, const void* buffer, int amount, sqlite3_int64 offset)
The VFS calculates the page number based on the offset. It then locates or creates the discrete file and overwrites it entirely with the newly modified binary payload from the buffer.11
xFileSize(sqlite3_file*, sqlite3_int64 *pSize)
The VFS must maintain an internal state tracking the highest page number written to the directory. It multiplies this maximum page number by the page size and writes the result to pSize to satisfy the Pager's bounds checking.11
xTruncate(sqlite3_file*, sqlite3_int64 size)
When SQLite issues a VACUUM command or deletes data, the Pager may truncate the database. The VFS divides size by the page size and issues file system unlink commands to physically delete any .bin files exceeding the new maximum page boundary.11

When SQLite is configured properly (e.g., via PRAGMA page_size = 4096), it divides its logical file space into 4KB segments.7 When the Pager requests to read 4096 bytes at offset 8192, it is logically requesting "Page 3" (since pages are 1-indexed in SQLite, though the offset math begins at zero). By isolating these requests, the architecture successfully shards the monolithic database.
4.2 Directory Sharding and Node Saturation
While writing individual page files solves the monolithic file problem, storing millions of pages in a single flat directory introduces severe operating system penalties. File systems such as ext4, NTFS, or APFS experience heavy degradation in directory traversal times when a single node contains hundreds of thousands of files. Furthermore, executing a git status or git add command over a flat directory of millions of files will result in unacceptably long computational times as Git attempts to construct its index.12
To mitigate this, the VFS must implement a sharded directory structure. Using the page number represented as a zero-padded hexadecimal string (e.g., Page 1048575 is 0xFFFFF), the VFS shards the storage into nested subdirectories based on the initial characters of the hex string:
/repository_root/.db/pages/0F/FF/0FFFFF.bin
By allocating two hexadecimal characters per directory level, the architecture guarantees a maximum of 256 subdirectories per level, and no more than 256 files per terminal directory. This deterministic tree structure dramatically accelerates OS file descriptor lookups and allows Git to traverse the working tree with maximum efficiency.
5. The Physics of Binary Delta Compression in Git
The most critical constraint addressed by this architecture is the efficiency of Git when storing binary files over time. A pervasive misconception in software engineering is that Git is fundamentally incapable of handling binary data effectively, leading to inevitable repository bloat.4 This is only true for compressed (e.g., JPEG, ZIP) or encrypted binary formats where a single logical mutation causes a cascading, catastrophic shift of all subsequent bytes, entirely defeating delta compression.13
5.1 The Cascading Byte Shift Phenomenon
To understand why the proposed page-to-file mapping is highly efficient in Git, one must contrast it with the behavior of a standard, monolithic SQLite file. Consider a monolithic 1GB .sqlite database. When a user executes an INSERT statement, SQLite may need to write the new payload into the middle of the file to maintain B-Tree key ordering. If the payload forces a page to overflow, SQLite must allocate a new page, shifting pointers and cascading changes throughout the file.
If this monolithic file is tracked by Git, a 50-byte insertion might alter the byte alignment for the remaining 500MB of the file. When Git attempts to calculate the difference between the old 1GB file and the new 1GB file, the cascading byte shift destroys the alignment of identical blocks. Git's compression algorithm fails to recognize the data as identical, forcing it to store massive, redundant binary snapshots, leading to severe repository bloat.4
5.2 B-Tree Internal Layout and Page Boundaries
The custom VFS architecture circumvents this completely by exploiting the internal structure of an SQLite B-Tree page. An interior or leaf page consists of a precise layout: a small 8-12 byte header (determining page type, free block start, and cell count), an array of 2-byte cell pointers growing downward from the header, an unallocated free space in the middle, and the variable-length cell payloads growing upward from the bottom of the page.7
When a new row is inserted into a specific page, the payload is written into the unallocated space, and a new 2-byte pointer is inserted into the cell pointer array.14 This causes a localized byte shift only within the cell pointer array of that specific page. Crucially, because the page files are rigidly separated at the VFS layer, a mutation inside Page 3 does not shift the bytes in Page 4. The cascading byte shift is contained entirely within the rigid boundaries of the 4096-byte file.2



5.3 Exploiting Git's xdelta Algorithm for Packfiles
Git does not compute differences when a commit is initially created; it stores full snapshots of modified files as loose objects (blobs) compressed via zlib.16 If the database is actively mutated, Git will accumulate multiple 4KB loose objects representing the historical states of 000003.bin.
However, during a repository repack (triggered automatically or via git gc), Git's internal garbage collection consolidates these loose objects into highly optimized binary "packfiles".18 The packfile generation engine relies on a modified version of the xdelta algorithm.20
Git's packing heuristic utilizes a sliding window algorithm that sorts objects by size, type, and path name before attempting to find deltas.20 Because the VFS names the pages consistently (e.g., 000003.bin), Git's heuristic will naturally group all historical versions of the exact same database page adjacent to one another in the sliding window.20
When Git compares Version 1 of the page to Version 2, it recognizes that despite the localized mutation in the pointer array, the vast majority of the 4096-byte file remains perfectly identical. The xdelta engine encodes the new version as a set of precise instructions: "Copy the first 120 bytes from Version 1, insert these 45 new bytes, then copy the remaining 3931 bytes from Version 1".17
The resulting delta payload is often only a few dozen bytes in size. Thus, storing millions of historical mutations of an SQLite database formatted in this manner will result in a shockingly compact Git packfile, completely solving the user's requirement for storage efficiency.19
6. Configuring Git for Optimal Binary Efficiency
While the architecture naturally aligns with Git's internal mechanics, specific configurations must be applied to the repository to guarantee that Git processes the binary pages optimally. Git's default behavior assumes that files without extensions are either plain text or unpredictable binaries, which can lead to suboptimal diffing attempts or the premature abandonment of delta compression.25
To strictly control this behavior, the application must automatically generate a .gitattributes file at the root of the database directory.12

7. Runtime Implementation: Pure C and Decoupled Architecture
The execution environment mandated by the revised architectural specifications is pure C. This approach completely eliminates the serialization bottlenecks and memory overhead associated with high-level runtime environments.
7.1 Native VFS Implementation in C
Because SQLite itself is written in C, extending it via a custom VFS is a native operation with zero integration overhead. Writing the code for a new VFS involves constructing a subclass for the sqlite3_vfs object and then registering that VFS object at runtime using a call to sqlite3_vfs_register().3 The custom VFS provides subclasses for sqlite3_file and sqlite3_io_methods to handle the page-to-file mapping natively.3 When SQLite invokes an I/O operation, the C function pointers execute directly, avoiding any context switching.
7.2 Decoupling Version Control from the Database Engine
To maintain maximum performance and adherence to the Unix philosophy of "do one thing well," the database engine itself does not integrate programmatically with Git. It does not link against third-party version control libraries, nor does it spawn expensive shell processes to handle commits. The C application's sole responsibility is translating SQL queries into disk I/O against the highly segmented VFS directory structure.
Git is treated entirely as an out-of-band operational concern. Because the C engine consistently formats and outputs the .db/pages/ files in a manner that perfectly aligns with Git's delta compression physics, the user is free to manage the repository externally using the standard Git Command Line Interface (CLI) installed on their system.
8. Transactional Atomicity and Out-of-Band Git Snapshotting
In contrast to systems that attempt to automatically generate commits on every database transaction, this decoupled architecture delegates version control triggers entirely to the user. This manual snapshotting approach allows users to group logical sequences of database changes into meaningful, distinct Git commits when they deem a milestone has been reached.
8.1 Local Crash Recovery vs. Versioned History
Because Git commits are not synchronized with SQLite's internal COMMIT statements, Git cannot be relied upon for instantaneous crash recovery of partial transactions. Therefore, the architecture must retain SQLite's standard rollback journal or WAL mechanism. When a user runs daily operations, SQLite manages ACID compliance natively via its standard xWrite and xSync operations, ensuring the .db/pages/ directory remains strictly consistent. Git serves exclusively as the macro-level version history and rollback mechanism, capturing snapshots of these stable states.
8.2 Out-of-Band Git Snapshotting
When the user determines the database is in a state worth versioning, they ensure active database write transactions are paused, and switch to their standard terminal to invoke Git CLI commands. The workflow is completely manual and requires zero custom application logic:
Stage: The user navigates to the repository root and stages all modified binary pages by executing git add. or git add.db/pages/.
Commit: The user commits the snapshot with a descriptive milestone message using git commit -m "Added Q3 financial datasets".
By delegating this completely to the user's standard toolchain, the C database engine remains incredibly lightweight, while the user retains full, unimpeded control over their version history without needing to learn a new abstraction layer. The underlying binary page architecture guarantees that Git will store these snapshots with maximal delta-compression efficiency natively.
9. Logical Merging and Conflict Resolution
The primary advantage of versioning a database with Git is the ability to leverage advanced distributed workflows: branching for experimental schemas, rolling back destructive operations, and merging disparate datasets. However, mapping a B-Tree structure onto Git introduces profound complexities regarding merge conflicts.
9.1 The B-Tree Conflict Dilemma
In systems natively designed for database versioning, such as Dolt, the Prolly Tree data structure is inherently path-independent.2 If two separate branches insert the exact same data, the resulting Prolly Tree blocks will possess identical cryptographic hashes, allowing for seamless, automatic merging at the block level.1
SQLite's B-Tree, conversely, is heavily history-dependent.1 The physical layout of the pages, the distribution of free blocks, and the order of pointers depend entirely on the specific chronological sequence in which rows were inserted or deleted.28 If Branch A and Branch B both insert a row into the database concurrently, they may both modify 000005.bin. When Git attempts to merge these branches, it will detect that a binary file has diverged. Because the files are arbitrary binary layouts rather than plaintext lines of code, standard text-based three-way merging is mathematically impossible. Git will simply halt and flag a binary conflict.30
9.2 Implementing Custom Logical Merge Drivers
To resolve this fundamental limitation, the merge process must be abstracted away from the physical binary page layer and elevated to the logical SQL layer. Git provides an extensible mechanism known as custom merge drivers, which can be configured via the .gitattributes file and .git/config.12
When a merge conflict occurs on any file within the .db/pages/ directory, Git can be configured to automatically invoke a standalone C executable designed specifically to handle SQLite merges. The architecture for this logical merge process operates as follows:
State Extraction: The standalone C merge driver instantiates two temporary, read-only SQLite connections via the custom VFS. One connection targets the state of the database at the HEAD commit (the current branch), and the other targets the state at the MERGE_HEAD commit (the incoming branch).
Logical Diffing: Because the system strictly adheres to the standard SQLite schema model, the merge executable can query the sqlite_schema table to dynamically discover all tables and indexes.32 It then performs full logical comparisons (utilizing primary keys, deterministic hashing, or modified-at timestamps) to extract the precise logical differences—the distinct INSERT, UPDATE, and DELETE statements—between the two branches.5
Conflict Resolution: If the same primary key was modified differently in both branches, a domain-specific resolution algorithm is applied (e.g., last-write-wins based on timestamps, or preserving the HEAD state).
Replay and Commit: The extracted, logically resolved SQL statements from MERGE_HEAD are systematically applied to the HEAD database.33 The VFS processes these writes normally, shifting bytes and balancing the B-Tree as required. Upon completion, the merge commit is finalized by Git.
By implementing this standalone logical merge driver, the architecture effectively circumvents the binary B-Tree conflict by reconstructing the merged state logically, providing the full power of Git versioning without sacrificing the performance or portability of the SQLite standard.
10. Conclusion
Implementing a robust, Git-versioned database while strictly preserving the query language, schema model, and portability of SQLite is a highly complex architectural endeavor. It cannot be achieved by altering foundational data structures—such as replacing B-Trees with Prolly Trees—without sacrificing strict upstream compatibility.
As established through this comprehensive analysis, the optimal solution leverages the lowest operational layer of the SQLite architecture: the Virtual File System (VFS). By authoring a custom VFS natively in C, the engine's contiguous logical address space is successfully mapped onto thousands of discrete, fixed-size binary page files, elegantly sharded to prevent operating system bottlenecks. Due to the immutable physics of fixed-size B-Tree pages, intra-page byte shifting is strictly contained. This containment allows Git's internal packfile heuristics and the xdelta algorithm to generate incredibly compact storage objects, storing historical database mutations with maximal efficiency.
Furthermore, by completely decoupling the database engine from the version control system, the architecture allows users to manually trigger versioned snapshots via the standard Git CLI when they deem necessary, ensuring the C application remains lightweight and singularly focused. Finally, while the history-dependent physical nature of B-Trees guarantees binary merge conflicts, configuring Git to utilize a custom standalone logical SQL merge driver ensures that the system provides the full suite of distributed version control capabilities. The resulting software architecture represents a seamless, high-performance integration of industrial-grade relational data management and cryptographic, history-independent version control.
